## 映射期（Intake + 说话人）

### P1 — 凭称呼判定说话人身份

- **坑**：原文里 A 被 B 叫"某老师"，直接把 A 当成那位老师。称呼可能是绰号/旧称/同音误听。
- **后果**：整篇说话人标错，数百回合全部归错人。
- **检测与修复**：角色指纹（谁主导什么）+ 时间线（何时到场）双重验证；用户首认只问最不确定的一个；修正后原话称呼词保留，头部加"称呼与标签不一致"说明。
- **教训**：称呼只能当线索，不能当结论。

### P9 — 时间线冲突未核对

- **坑**：没核对"X 在 [HH:MM:SS] 才到场"的早段回合。
- **后果**：说话人误识别遗留。
- **检测与修复**：每人第一次 ASR 出现时间 vs 在场最早时间；冲突回合撤销改动、恢复原归属、标"口误/存疑"。任何映射改动后重跑时间线核对。

### P11 — 把「用户确认过」当绝对真理锁死

- **坑**：用户首次回答映射问题后，AI 不再保留追问余地。
- **后果**：用户首次回答基于不完整信息，错位要用户主动纠正才发现。
- **检测与修复**：首次确认只问最不确定的一个；新矛盾（"主导 X 的应该是 Y"对不上映射）出现时立即回原文复核。
- **教训**：用户确认是证据，不是终点。

### P16 — 阶段①一次问完所有映射

- **坑**：一次性问"说话人2 是谁？说话人3 是谁？……"
- **后果**：用户凭直觉猜，AI 把猜测锁死。
- **检测与修复**：只问最不确定的那一个，其余靠指纹+时间线+后续追问补齐。

### P37 — 委派场的映射初判可能错

- **坑**：主对话快速初判映射（"疑为某人"）直接交给子代理。
- **后果**：整场清洗稿人名错。
- **检测与修复**：抽验 00/01 时对照跨场硬证据（合同/付款/项目名）；错则当场订正+标签批量替换（走 P18 波及清单）。

## 清洗期

### P2 — 漏写右 `】` 致金句格式失效

- **坑**：`Write` 批量写时写成 `**【某人** [00:00:39]`（缺 `】` 和第二个 `**`）。
- **后果**：渲染器识别不了 → 整篇金句丢失交互。
- **检测与修复**：

```bash
grep -cE '^\*\*【[^】]*\*\* \[' 01_清洗稿.md   # 应 = 0
# 修复（按本场人名改模式）：
sed -i '' -E 's/^\*\*【(人名1|人名2)\*\* /**【\1】** /' 01_清洗稿.md   # macOS
```

### P7 — Write 超长静默截断

- **坑**：一次写 > 5 万字节或大量特殊字符，文件被截到一半且**无报错**。
- **后果**：文件半截、内容丢失。
- **检测与修复**：分块写（Write 头部带锚点 → Edit 逐块替换锚点追加 → 末尾清锚）；写完 `wc -l` 对比预期、`tail` 看末尾完整。

### P12 — ASR 订正不写对照表

- **坑**：订正了错字但没登记。
- **后果**：读者分不清订正还是臆改。
- **检测与修复**：所有订正进头部 `| 原词 | 还原 | 说明 |` 表；不确定的标 `[ASR/存疑]`。

### P14 — 闲聊段一字不删全保留

- **坑**：为了"忠实"，闲聊琐碎全量保留。
- **后果**：清洗稿虚胖，主题整理重读 80% 无关内容。
- **检测与修复**：闲聊段标【闲聊】，纯琐碎明确写"从略"，登记忠实性说明。

### P24 — 01 正文回合内加粗

- **坑**：正文回合里给词语 `**加粗**`。
- **后果**：02/05/08 引文按纯文本逐字比对，星号混进被引句子 → 逐字校验全炸（一次 17 行返工）。
- **检测与修复**：01 正文回合一律不加粗——强调用 `[标注]` 或叙述表达；加粗只属于 02-09 结构层。

### P26 — 重写 01 后不重核下游；无时间戳续段

- **坑**：升级/重写 01 后直接交付，旧版产出的 02/05/08 引文全部失配；长回合手动换行成无时间戳的续段（校验脚本只读回合首行）。
- **后果**：一次 29 处硬伤。
- **检测与修复**：① 重写 01 后全量重跑 verify_quotes 并逐处修；② 长回合整行写完或在自然句边界拆独立回合（各带时间戳）；③ 续段扫描：正文非空行且不以 `**【/#/|/>/- ` 开头即续段，拆回带原始时间戳的独立回合。

### P27 — 分段读原文时脑补衔接段

- **坑**：超长原文分段 Read，没读到的区间凭上下文"应该是这样"补写回合。
- **后果**：清洗稿出现无中生有的"原话"——核证链彻底断裂，比错字严重一个量级（诚实红线）。
- **检测与修复**：分段读时头尾衔接段必须回查原文（重读上一段末尾几行）；拿不准的区间宁可不写、标「[衔接段未读，待补]」。

### P35 — 口吃重复是原文保真的一部分

- **坑**：终校报失配时"顺手修正"原文口吃（"前面/前端"类）。
- **后果**：破坏金句原话一字不改原则。
- **检测与修复**：报失配先查原文是否口吃，是则改校验预期而非原文。

### P45 — 合并回合吞掉下游引用时间戳：verify 报「时间戳不在 01 正文」

- **坑**：清洗时按「同人碎片合并保留首时间戳」把多个原始 ASR 回合并成一回合，下游 02/05/08 引文若引用了被吞的中间时间戳（金句常落在回合中部），verify_quotes 报「时间戳不在 01 正文（疑指向被合并段）」。
- **后果**：要么硬伤返工，要么清洗者改引文时间戳迁就 01（丢精度）。
- **检测与修复**：报错信息即检测。修复优先级：① 若该时间戳处有独立语义单元（金句/被引用句），把 01 合并回合**按原始时间戳拆回**；② 确属碎片才改引用指向段首。
- **教训**：预计会被 02/05/08 引用的段落（金句密集区、收尾总结段），清洗合并要保守——按原始时间戳保留回合边界，宁可回合多不可时间戳丢。

## 提炼期（模块产出）

### P3 — 金句/字段头写错

- **坑**：漏星号/括号、时间戳格式错（`0:00` 而非 `00:00:SS`）、字段头 `**核心**：` 漏冒号。
- **后果**：渲染器静默不识别，内容在 HTML 里丢失交互。
- **检测与修复**：模板照 `references/03` 复制；verify_quotes 抓时间戳问题。

### P4 — 议题/洞察地图不用 ``` 代码块

- **坑**：ASCII 图写在普通段落里。
- **后果**：渲染为普通段落，结构丢失。
- **检测与修复**：图前后加三连反引号；`awk '/^```$/{c++} END{print c}'` 应 ≥2。

### P5 — 给圆桌/闲聊硬加战略诊断

- **坑**：所有场都套"战略诊断"腔。
- **后果**：没有甲方和行动的对话硬加会很别扭。
- **检测与修复**：阶段①判类型；凡有待办即出 09（行动清单），无待办不出。

### P6 — 洞察卡不写反方

- **坑**：只有核心+证据+启示。
- **后果**：洞察变断言。
- **检测与修复**：反方数应=卡数；质量分级见 `references/03`（A 场内对立 > B 边界 > C 风险剧本）。

### P17 — 「启示」写成金句引用

- **坑**：启示字段再引一遍原话。
- **后果**：启示=金句重复，没给出用法。
- **检测与修复**：启示写 2-4 句"具体怎么用"。

### P21 — 跨层复制正文而非存引用

- **坑**：同一金句在 01 附录、02 段文件、08 证据出现 3 次；03/08 同题率 50%；04 混三种词条。
- **后果**：改一处漏两处；读者重复阅读；跨场无法归并。
- **检测与修复**：金句引用制（真身只在 01）；03/08 互斥判据；04 只留外部名词+指针。

### P22 — 空洞反方骗过数量检查

- **坑**：「也可能不成立，要看具体情况」类占位符反方能通过"反方数=卡数"检查。
- **后果**：洞察卡退化成断言+免责声明。
- **检测与修复**：verify_quotes 警告级（反方 <12 字或匹配敷衍黑名单）；按反方分级重写。

### P23 — 引文时间戳张冠李戴

- **坑**：把别的回合的句子拼到某时间戳名下；或引用了被合并段的源时间戳。
- **后果**：按时间戳跳转落空或坐错位置；核证链断裂。
- **检测与修复**：verify_quotes 硬伤级（exit 1）；改指合并段首时间戳；引文对齐 01 逐字。

### P25 — 段文件/术语/时间戳不守渲染契约

- **坑**：段文件没按 `第N段_*.md` 命名；术语没用 `###`；时间戳写短格式。
- **后果**：render_pack **静默提出 0**（不报错）；引文校验报硬伤。
- **检测与修复**：契约见 `references/03`——段文件 `第N段_主题.md`、术语 `###`、时间戳一律 `[HH:MM:SS]`。

### P31 — 凭印象写引文时间戳

- **坑**：02/05/08 引文的 ts 凭对原始转写的印象写，与清洗合并后的回合首错位。
- **后果**：verify 报「不逐字」（易误判为措辞问题去改字，实际是 ts 指错回合）。
- **检测与修复**：报「不逐字」时先 `grep "^\*\*【人】\*\* \[ts\]" 01` 看该回合实际内容再决定改哪个；引文一律从写好的 01 逐字复制+复制其行首 ts。
- **教训**：统计类 grep 必须锚定行首 `^\*\*【` 模式（头部对照表也含时间戳字样，会污染结果）。

### P42 — 凭记忆写引文：截断标点失真+省略号删节

- **坑**：通读 01 后凭记忆写引文：长句截断处把「，」写成「。」；省略号删节（官方校验按整回合比对、不认省略号）。
- **后果**：批量假性失配，淹没真问题。
- **检测与修复**：引文一律从 01 复制**完整连续子串**（句读自然处收尾、禁省略号删节、禁改标点）；放行标准唯一=官方 verify_quotes 硬伤 0，替代预检脚本仅作辅助。

## 渲染与交付期

### P8 — 没立刻 grep 自检就交付

- **坑**：写完觉得对了直接交付。
- **后果**：P2 类 bug 漏到交付。
- **检测与修复**：写完立刻跑质量门禁（`references/05`），不能跳。

### P13 — 跨场复制渲染器代码

- **坑**：上一场的 HTML 生成代码复制过来改。
- **后果**：CSS/JS 重复维护，改一处同步多场。
- **检测与修复**：monkey-patch 复用母版（`import build_html as B` 覆盖差异点），见 `references/04`。

### P15 — 时间戳跳不进/跳错

- **坑**：金句时间戳与清洗稿/页面内目标不一致。
- **后果**：点击跳不到对应位置。
- **检测与修复**：金句 ts 逐一在 01 grep 验证存在；跳转交互边界见 `references/04`。

### P29 — CSS 同特异性后者覆盖

- **坑**：修样式时扩大作用域，与既有容器规则同特异性且写在后面——后者胜。曾出现"蓝底灰字看不清"：颜色值都"正确"，机械自检查不出层叠顺序。
- **后果**：修一个缺陷引入另一个渲染缺陷。
- **检测与修复**：改 CSS 作用域前列出所有会命中的既有容器，逐项核对覆盖关系；改完人眼看打样页受影响区块。

### P39 — 质检脚本 `open(f,'w').write(open(f).read())` 清空文件

- **坑**：Python 先执行 `open(f,'w')`（此刻文件即被清空），再求值参数读到空文件，最终 write('')。本意的 no-op 毁文件。
- **后果**：场次文件被清空（实战清空过一个段文件）。
- **检测与修复**：读与写分离两条语句；「本不打算改文件」的步骤根本不出现 `'w'` 模式；脚本操作后 `ls -la` 看大小。
- **教训**：管线里最危险的是主对话临时起意的"顺手脚本"。

### P46 — macOS bash 3.2 下 pipeline_check 人名回合计数假 0（多字节三坑）

- **坑**：macOS 自带 /bin/bash 3.2 + BSD 工具链在 UTF-8 下三处连环坑：① 双引号模式串 `"...【$n】..."` 里 `$n` 周边多字节字符被部分吞噬（`周明` 6 字节塌成 2 字节）；② BSD sed 对含 `【】` 的中文替换乱码（人名提取直接搅坏）；③ `LC_ALL=C` 可修①但让 `[^】]` 否定类退化为字节级（含 `】` 任一字节的中文全被排除）。
- **后果**：计数假 0 易被误读为「清洗稿回合全丢/标签全错」引发返工，或养成无视检查 1 的习惯。
- **检测与修复**：脚本计数显示 0 而产物明显有回合时，先怀疑工具——用 python 交叉复测。**已修（v3.1.1）**：pipeline_check 的人名提取与检查 1 计数整体改走 python3 子进程（提取与计数同源一次完成），三坑一并绕开；脚本报告数字与 python 权威统计一致。
- **教训**：门禁脚本自身的运行环境也是变量；「脚本说 0」与「文件真是 0」要用第二种独立方法交叉验证后才下结论。

## 跨场次与全局层

### P10 — 子目录命名混乱

- **坑**：产物子目录和原始逐字稿放同一位置。
- **后果**：产物与素材不分，跨场对照困难。
- **检测与修复**：固定 `<场次名>_YYYY-MM-DD/`；原始逐字稿留原位置不动。

### P18 — 身份订正跨文件扩散

- **坑**：订正人名只改了 01 头部与部分正文，波及 8 个位置漏改。
- **后果**：同一人物在 8 文件两种写法；跨场人物链条断裂。曾 3 轮 grep 才清完。
- **检测与修复**：订正后必跑 pipeline_check；波及清单全过：01（头部/对照/正文/附录）/02（含段文件名）/03/04（词条标题）/05（卡标题/代表发言标签）/06/07/08/09/README；`grep -rn "旧名" --include="*.md" . | grep -v "曾作\|原文\|疑"` 应为空。

### P19 — 云端重复上传

- **坑**：转写云盘同一音频可能被 AI 起不同标题二次上传；ID 与标题都不同。
- **后果**：增量拉取重复落盘，同场录音两条。
- **检测与修复**：两条头尾/字数/时长全同时先 `md5` 校验；重复只留先到一条，索引注明并档。

### P20 — 主题总 README 与总览 HTML 断档

- **坑**：只更新场次 README 与主题链表，总览 HTML 忘了追加。
- **后果**：总览入口链接 404，只看得到旧场次。
- **检测与修复**：每场完成后 pipeline_check 第 6 项自动校验总览链接 + 手工追加。

### P30 — 同日多场的原子 id 撞号吞并

- **坑**：extract_atoms 的原子 id 只含日期，同日多场 id 完全重叠，后入库场被"按 id 去重"整场吞掉。
- **后果**：实战曾 10 个场次数百条原子从未入库，且无任何告警。
- **检测与修复**：id 生成按目录名排序给同日场次加 b/c/d 后缀；检测：`python3 -c "import json; from collections import Counter; c=Counter(json.loads(l)['session'] for l in open('<项目根>/<全局层目录>/atoms.jsonl')); print({k:v for k,v in c.items() if k[-1] in 'bcd'})"`。
- **教训**：id 生成的粒度必须与真实实体粒度一致——场次才是实体，日期只是属性。

### P32 — 撞号修复后按当日排序分配≠历史入库顺序，静默复发

- **坑**：撞号修复按当日目录排序分配后缀，但历史无后缀槽位实际归历史第一个入库的场——排序翻转的场继续丢，状态看起来"已修复过"。附带坑：05 小节头（「以下为被提及者」类）误入为 person 原子。
- **后果**：重复+丢失并存，无告警。
- **检测与修复**：① 同 id 不同内容从静默吞没改为响亮告警；② 清理幽灵原子时逐条断言副本存在才删，勿用槽位号假设；③ 05 小节头避免用 `## `（被提及类小节用其他级别）。
- **教训**：修「按 key 去重吞并」类 bug 必须验证 key 的历史归属与新规则一致；去重工具对"同 key 不同内容"必须报警，静默即数据黑洞。

### P40 — 外部归档进程与管线 Write 并发竞争

- **坑**：会话中途另一进程把场次目录归档/移动/留软链，与管线 Write 竞争。丢文件（Write 返回成功但事后找不到）+ 目录分裂（软链被删后沿旧路径重建真身，产物分居两处）。
- **后果**：渲染器只读到一半产物。
- **检测与修复**：交付前 `readlink <场次目录>` 与两处 `ls` 对照（空=真目录）；01 与 00-09 必须同目录；归档活跃时段每写完一批立即 `ls` 验数；质检脚本对嵌套目录的路径假设会产生假阴性，以 python 权威统计为准。

### P44 — 合并包跨场撞键：verify_quotes 误报前场引文「不逐字」

- **坑**：多场连读合并包（一份 01 收录多场）各场时间戳独立从 00:00:00 起，同说话人+同时间戳（两场都有 `**【某人】** [00:03:42]`）时，verify_quotes 的 turn_map 单值取后场覆盖前场——前场该时间戳的真实引文被误报「引文不逐字」。
- **后果**：忠实无误的引文被判硬伤，清洗者会去「改引文迁就校验」，反而破坏逐字忠实。
- **检测与修复**：合并包跑出「不逐字」但 grep 01 能找到逐字原文、且同 (人, ts) 存在两条 → 撞键。修复：turn_map 按 `(人, ts)→[文本列表]` 列表化，任一命中即通过（已修入脚本）。
- **教训**：校验器报错先分辨「内容错」还是「校验基底错」——时间戳非全局唯一的场（合并包/双源场），查表类校验必须列表化。

## 子代理模式

### P28 — 子代理输出超限静默终止；回报失真

- **坑**：轻量模型子代理一次输出超 32K 被静默终止（无输出纪律的批次 5/6 失败）；回报的金句时间戳与实际不符。
- **后果**：批量清洗丢场、引文错位。
- **检测与修复**：派发模板必带「输出纪律」（中间回复 ≤2 句、每块 ≤80 行、长内容只进文件）；子代理产出的引文必须回 01 grep 重新定位，不信任代理报的时间戳；主对话逐场跑 pipeline_check + verify_quotes。

### P33 — 子代理版 01 用自定义骨架，verify_quotes 识别不了

- **坑**：子代理产出的 01 结构非标准（骨架自定），官方校验跳过 → 引文无校验。
- **后果**：假绿灯。
- **检测与修复**：用「引文终校」替代脚本（02/08 引文 vs 01 归一化子串：strip 括注 → norm 标点 → `in` 判断，顺序不能反）；或让子代理严格按标准骨架产 01（附录 A 在文末、标题带 ·）。

### P34 — 主对话凭记忆写 02/08 引文（委派场变体）

- **坑**：委派模式下主对话没亲手洗稿，凭通读印象写引文 → 删节失配。
- **检测与修复**：引文必须从 01 grep 实文复制，禁止凭阅读记忆写。

### P36 — 委派 prompt 误带不存在的金句

- **坑**：给子代理的"金句候选"里混入自己记忆中（实际不在本场）的句子。
- **检测与修复**：子代理应拒录并报告；主对话发 prompt 前把候选金句 grep 原文确认存在。

### P38 — 忠实度抽验的「±秒窗口拼接法」系统性误报

- **坑**：抽验按「原文同时间戳 ±60s 窗口拼接取前 N 字比对」实现，但清洗方向是向后合并（同讲者碎片并成长回合、保留首时间戳），回合正文跨度常超窗口 → 参考文本错位，比率可跌到 0.3-0.4 触发假警报（正常 0.65-0.85+）。
- **检测与修复**：抽验异常低时，先用「理应一字不改」的回合（指令/金句）精确锚定复测——精确锚定达标而窗口法低 = 抽验方法问题；抽验一律「同时间戳块为锚 + 向后相邻 1-4 块拼接取最优」。

### P41 — 子代理把附录 A 放头部：校验基底被附录 B 覆盖

- **坑**：子代理把「小节索引（附录 A）」放在 01 头部且标题带括号 → verify_quotes 的 `body.split('## 附录 A', 1)[0]` 切不中 → turn_map 含正文+附录 B 全部回合 → 同 (人,时间戳) key 冲突、附录 B 短金句覆盖正文长回合 → 长引文批量假性「不逐字」。
- **检测与修复**：附录 A 移到文末、标题写 `## 附录 A · 小节索引`；伴生坑：子代理按源格式产 [MM:SS] 短时间戳，主对话须统一规范化为 [HH:MM:SS]（含节标题区间行）。
