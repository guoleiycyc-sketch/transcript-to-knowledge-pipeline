# Pitfalls 库（持续累积）

每次新场次执行时，往这里加新发现的坑。**活文档**——不要等大重构才更新。

每个坑记录：

- **陷阱描述**：出错的具体场景
- **后果**：对产物的实际影响
- **检测命令**：如何发现
- **修复方法**：如何修
- **首次发现**：日期 + 场次

---

## P1 — 凭称呼判定说话人身份（08-09 场 / 2026-08-09）

**陷阱描述**：原文里 A 被 B 叫"D"（或其他尊称），AI 把 A 当成"D"。

**后果**：整篇说话人标错。本场：把说话人3（=C）当D、把C当隐形人，214 回合全部归错人。

**检测方法**：

- 自查：被叫的称呼 ≠ 该人的本名。称呼可能是绰号 / 旧称 / 同音误听。
- 必须用**角色指纹**（谁主导什么）+ **时间线**（X 何时到场）双重验证。

**修复方法**：

- 用户首次确认只问最不确定的那一个，保留追问余地
- 任何矛盾（用户说"主导 X 的是 Y"）→ 立即回原文复核
- 修正后：原话称呼词保留（金句原则），头部说明"称呼与标签不一致"

**首次发现**：2026-08-09 场，用户主动纠正"主导做商业规划的是C"。

## P2 — 漏写右 `】` 导致金句格式失效（08-09 场 / 2026-08-09）

**陷阱描述**：`Write` 批量写回合格式时漏 `】`，写成 `**【B** [00:00:39] 原话`（缺 `】` 和第二个 `**`）。

**后果**：渲染器识别不了金句格式 → HTML 里没有可点击金句卡 → 用户最值钱的内容丢失交互。

**检测命令**：

```bash
# 应输出 0
grep -cE '^\*\*【[^】]*\*\* \[' 01_清洗稿.md
```

08-09 场漏了 666 行。

**修复命令**：

```bash
# macOS
sed -i '' -E 's/^\*\*【(人名1|人名2|人名3|人名4)\*\* /**【\1】** /' 01_清洗稿.md
```

修复后**再跑一次**确认 = 0。

**首次发现**：2026-08-09 场，写完 1207 行后 grep 自检发现。

## P3 — 金句速查、原文节选、字段头写错

**陷阱描述**：

- 漏 `**【...】**` 的星号或括号
- 时间戳格式错（写成 `0:00` 而非 `00:00:SS`，或缺冒号）
- 字段头 `**核心**：` 漏冒号或拼错

**后果**：render_pack 不识别 → 这些内容在 HTML 里丢失（金句卡不能点、洞察卡没反方）

**检测命令**：

```bash
# 金句格式
grep -cE '\*\*【[^】]+】\*\* \[[0-9]{2}:[0-9]{2}(:[0-9]{2})?\]' 01_清洗稿.md
# 字段头
grep -cE '^\*\*核心\*\*|^\*\*证据\*\*|^\*\*启示\*\*|^\*\*反方\*\*' 08_洞察卡片.md
```

**修复方法**：模板在 `references/07-templates.md`，照搬。

## P4 — 议题地图 / 洞察地图不用 ``` 代码块

**陷阱描述**：ASCII 图写在普通段落里（缩进或裸文本），没用 ``` 包裹。

**后果**：渲染为普通段落 → 视觉乱 → 结构丢失

**检测命令**：

```bash
# 应≥ 2（议题地图 + 洞察地图各至少一个）
awk '/^```$/{c++; if(c>=2) exit} END{print c}' 07_议题关联地图.md
awk '/^```$/{c++; if(c>=2) exit} END{print c}' 08_洞察卡片.md
```

**修复方法**：ASCII 图前后加三连反引号。

## P5 — 给圆桌/闲聊硬加 09 战略诊断

**陷阱描述**：把所有场都套上 09_战略诊断与行动清单。

**后果**：圆桌/闲聊没有"甲方+行动"，硬加会很别扭。

**检测**：阶段 ① 已判断类型，只在咨询/诊断类加 09。

## P6 — 洞察卡片不写反方

**陷阱描述**：每张洞察卡只有核心+证据+启示，漏了反方/边界/张力。

**后果**：洞察变成断言，不是洞察——好的洞察往往是"正面成立但有个边界"。

**检测**：

```bash
# 反方数应 = 卡片数
grep -cE '^\*\*反方\*\*' 08_洞察卡片.md
grep -cE '^## 卡 [0-9]+' 08_洞察卡片.md
```

**修复**：每张卡必须写反方（场内对立观点 / 适用条件 / 反例 / 风险条件）。

---

## P7 — Write 超长截断

**陷阱描述**：`Write` 一次写超大文件（> 5 万字节 + 大量特殊字符）会被截断到一半。

**后果**：文件半截，内容丢失，无报错（不报错！）

**检测**：写完立刻 `wc -l` 对比预期行数；`tail` 看末尾是否完整。

**修复方法**：分块写。Write 头部+前几节带唯一锚点 → Edit 替换锚点追加中段 → 末尾去锚。

---

## P8 — 没立刻用 grep 自检就交付

**陷阱描述**：写完觉得对了，直接交付。

**后果**：P2 类 bug 漏到交付。

**修复**：写完**立刻**跑 6 次检查（见 `references/05-quality-checks.md`）。不能跳。

---

## P9 — 时间线冲突未核对

**陷阱描述**：说话人识别时，没核对"X 在 [HH:MM:SS] 才到场"的早段回合。

**08-09 场例子**：C [00:20:07] 才到场，但 §1 [00:15:32] A说"C谈谈你"——如果按字面意思拆出C回合，时间线不符。

**检测**：每个说话人的第一次 ASR 出现时间 vs 该人物在场的最早时间。

**修复**：撤销冲突回合，保留原 ASR 归属，标注"口误/存疑"。

---

## P10 — 子目录命名混乱

**陷阱描述**：产物子目录和原始逐字稿放在同一位置，命名混在一起。

**后果**：分不清产物 vs 原始素材；跨场对照困难。

**修复**：固定子目录命名 `<场次名>_YYYY-MM-DD/`（如 `企业级AI Agent商业化讨论_2026-08-09/`）。原始逐字稿留在原位置不动。

---

## P11 — "用户确认过"= 绝对真理

**陷阱描述**：AI 把用户首次回答当绝对真理锁死，不保留追问余地。

**08-09 场例子**：

> 我问"说话人2 是谁"，用户答"B"
> 我同时假设"说话人3 = D"（因为原文里A叫说话人3 老师）→ 用户没纠正
> 几小时后用户主动纠正"主导商业规划的是C" → 我才发现整篇说话人标错

**后果**：大量错位 + 用户必须主动纠正才会发现。

**修复**：

- 首次确认只问最不确定的一个
- **永远保留追问余地**
- 一旦新矛盾出现，立即复核，不要让假设"先跑了再说"

---

## P12 — ASR 订正不写对照表

**陷阱描述**：清洗时订正了 ASR 错字，但没在头部 ASR 对照表里记录。

**后果**：读者看不到还原依据，不确定是订正还是臆改。

**修复**：所有订正写进对照表 `| 原词（ASR）| 还原 | 说明 |`；不确定的标 `[ASR/存疑]`。

---

## P13 — 跨场复制渲染器代码

**陷阱描述**：上一场 HTML 生成代码复制过来改。

**后果**：CSS/JS 重复维护，每次改一处要同步多场。

**修复**：monkey-patch 复用首场渲染器，`import build_html as B` 后覆盖 `B.SEG_META`/`B.PEOPLE_*`/`render_overview` 等差异点。

跨项目复用时 `sys.path` 用绝对路径指向首场 `_工作文件`。

---

## P14 — 闲聊段一字不删地全保留

**陷阱描述**：为了"忠实"，把电车闲聊、酒店入住、吃东西、充电宝等全保留。

**后果**：清洗稿 1500+ 行，主题整理时 80% 内容要重读一遍才能挑出业务相关。

**修复**：闲聊段保留对话但**小节标注【闲聊】**，并对纯琐碎（与主线无关）的明确写"从略"。详见 08-09 场 §2.5、§3 末尾、§17。

---

## P15 — 时间戳跳不进 / 跳错

**陷阱描述**：清洗稿时间戳和 HTML 金句里的时间戳不一致。

**后果**：点击金句跳不到原文位置。

**修复**：清洗稿写完后，把金句速查的 8 条时间戳逐一在清洗稿里 grep 验证存在。HTML 跳转用相对路径或锚点。

---

## P16 — 阶段 ① 就问用户所有映射

**陷阱描述**：一次性问完所有说话人映射（"说话人2 是谁？说话人3 是谁？D是谁？"）。

**后果**：用户可能答不全（信息不全时凭直觉猜），AI 把猜测当真理锁死。

**修复**：阶段 ① 只问**最不确定的那一个**（通常是被 ASR 标"说话人2"的那个，因为"A"是 ASR 直接标注的）。其他用角色指纹+时间线+后续追问补齐。

---

## P17 — Insight 卡"启示"写成金句

**陷阱描述**：启示字段里写成了"原话引用"而不是"怎么用这个规律"。

**后果**：启示变成金句重复，没给出可执行的用法。

**修复**：模板见 `references/07-templates.md`，启示字段写 2-4 句"具体怎么用"。

## P18 — 身份订正的跨文件扩散（2026-08-19 / 客户丁场）

**陷阱描述**：本场首次出现真实订正（转写账号名 X = 真人 F、误写变体 = 真人 G 的正字、误听变体 = 真人 H、另一变体疑同真人 H）。第一轮只替换了 01 头部映射与部分正文，靠 grep 复检又跑了 **3 轮**才清完 07/08/09/README 残留。

**后果**：跨场人物链条断裂（其他场提到「G」/「X」会与本场冲突）；同一人物在 8 个文件里有 2 种写法，主题总 README 与总览 HTML 也漏更新。

**检测**：详见 `references/08-cross-session-sync.md` 第一点的波及检查命令。

**修复方法**：

- 订正后**必跑** `scripts/pipeline_check.sh <场次目录>`（含人名一致性 + 跨会话同步）
- 波及清单 8 点全过：01（头部/对照/正文/附录）/02（含段文件名）/03/04（含词条标题）/05（人物卡标题/代表发言标签）/06/07/08/09/README
- 同步人物映射记忆（账号名陷阱记录）+ 进度记忆（新场次摘要）

## P19 — 云端重复上传陷阱（2026-08-19 / 得到大脑增量）

**陷阱描述**：得到大脑同一个音频可能在数分钟后被 AI 自动起不同标题二次上传。两次 detail API 拉回的 `audio.original` 内容完全相同（MD5 一致），但 ID 与标题都不同。

**后果**：增量拉取若不校验，会重复落盘、目录里多出两条同一场录音；`笔记CLI notes` 列表无法看出重复，只能靠头尾/字数/时长/MD5 二次校验。

**检测**：

```bash
# 新拉取的两条若头尾/字数/时长全同：
md5 <file1> <file2>
# 相同 → 保留先到一条，重复件删除
```

**修复方法**：增量拉取工作流加一步 md5 校验；`_索引.md` 注明并档（见 `dedao-brain-transcript-fetch.md`）。

## P20 — 主题总 README 与总览 HTML 断档（2026-08-19）

**陷阱描述**：本场（第 19/20 场）完成后只更新了场次 README 与主题总 README 链表，但 `_渠道与交付战略_五场总览.html` 仍停在 5 场——主题成果层与总览层出现 5 场差距。

**后果**：总览页面链接断链（指向第 6/7/8/9 场 → 404），用户从总览入口只能看到五场。

**检测**：`bash scripts/pipeline_check.sh <场次目录>` 中的检查 6 自动校验总览 HTML 链接。

**修复**：每场完成后必跑 pipeline_check.sh 第 6 项 + 手工追加总览 HTML 链表。

## P21 — 跨层复制正文而非存引用（2026-08-19 / 三方评审）

**陷阱描述**：同一句金句在 01 附录、02 段文件、08 证据出现 3 次；03 方法论与 08 洞察卡同题率 50%（"三部曲""做没了""成本切分"同时出现在两处）；04 术语表混人名/方法论/外部名词三种词条。20 场实测确认。

**后果**：修改一处漏两处（身份订正时波及 8 文件跑 3 轮才清完）；读者重复阅读；跨场无法归并同题资产。

**检测**：见 `references/03` v2 规范各判据；pipeline_check.sh 检查 2 的同题检测。

**修复**：
- 金句引用制（07 模板 v2 格式）
- 03/08 互斥判据（03="遇 X→执行 Y"、08=必有反方禁操作）
- 04 只留外部名词，人名/方法论用指针
- 根治=第三批单库多视图（atoms.jsonl + render_views.py）

**首次发现**：2026-08-19，知识管理/咨询/定性研究三方评审共识。

## P22 — 空洞反方通过数量检查（2026-08-22）

**陷阱描述**：「反方数=卡片数」的检查只防漏写，不防敷衍——「也可能不成立，要看具体情况」这类占位符反方能拿 ✓ 通过。

**后果**：洞察卡退化成断言+免责声明，反方失去「边界/张力」的论证功能。

**检测**：
```bash
python3 scripts/verify_quotes.py <场次目录>
# 警告级：反方 <12 字 或匹配敷衍模式（也可能不成立/要看具体情况/因人而异/凡事都有两面…）
```

**修复**：按 references/03「反方质量分级」重写——A 场内对立引文 > B 边界条件 > C 风险剧本；反方须含具体名词或条件从句。

**首次发现**：2026-08-22，构造样本验证旧检查放行两张敷衍反方（RED 测试）。

## P23 — 反方/证据引文时间戳张冠李戴（2026-08-22）

（编号注：本条与上条原误编 P13/P14，与既有条目撞号，2026-09-04 顺延为 P22/P23。）

**陷阱描述**：写 08 卡时把别的回合的句子拼到某时间戳名下（08-21 场：[01:00:47] 的引文实为 [01:00:38] 的原话）；或引用了被合并段的源时间戳（正文已并入段首）。

**后果**：读者按时间戳跳转落空或坐错位置；金句「原话一字不改」的核证链断裂。

**检测**（同上 verify_quotes.py，硬伤级 exit 1）：
1. 引文 (人, 时间戳) 必须命中 01 正文回合首
2. 引文逐字（省略号切段；两侧对称剥离圆括号括注后须为子串）

**修复**：改指合并段首时间戳；引文对齐 01 逐字（括注写括号里）。

**首次发现**：2026-08-21 场全量审校，一次抓出 5 处时间戳错位 + 11 处不逐字。

## P24 — 01 正文回合内加粗，炸掉下游引文逐字校验（2026-08-31 / 第 40 场）

**陷阱描述**：清洗稿正文回合里给词语加 `**加粗**`（如强调关键概念）。02/05/08 引文按纯文本逐字比对，星号一旦混进被引用的句子 → verify_quotes 逐字失配。

**后果**：本场 17 行返工；verify 大量硬伤误报淹没真问题。

**修复**：**01 正文回合一律不加粗**——强调用 `[标注]` 或叙述性文字表达；加粗只用于 02-09 的结构层。verify_quotes 已机械兜底，但写时不加粗才是治本。

## P25 — 渲染器/校验器的文件名与格式硬依赖（2026-09-02 / 第 38 场）

**陷阱描述**：02 段文件没按 `第N段_*.md` 命名；04 术语表条目没用 `###` 三级标题；时间戳写成 `[MM:SS]` 短格式。

**后果**：render_pack 静默提出 0（段:0 / 术语:0，不报错）；verify_quotes 对短格式报 5 处硬伤。

**修复**：段文件固定 `第N段_主题.md`；04 条目固定 `###`；时间戳一律 `[HH:MM:SS]` 全格式。这些是渲染契约（references/07 / format-templates），不是风格偏好。

## P26 — 重写 01 后未全量重核下游引文；续段不被 verify 读取（2026-09-03 / 第 42 场）

**陷阱描述**：把 01 升级「详细版」（补回口误叠字、增删字、跳句）后直接交付——旧版产出的 02/05/08 引文全部失配。另：长回合写成无时间戳的换行续段，verify 只读带时间戳的回合首行，续段里的引文天然失配。

**后果**：本场一次性 29 处硬伤。

**修复**：① 重写 01 后必须全量重跑 verify_quotes 并逐处修 02/05/08；② 长回合要么整行写完、要么在自然句边界拆成独立回合（各带时间戳）；③ 写 02 引文前先 grep 01 确认原句逐字形态（「就/就是」「我能/我可以」类字差最易混）。

## P27 — 分段读原文时脑补衔接段（2026-09-02 / 第 38 场）

**陷阱描述**：超长原文分段 Read 时，两段之间没读到的区间，凭上下文「应该是这样」补写出看似合理的回合。本场 §C1 曾臆造 [00:01:40]-[00:02:08] 四个不存在的回合。

**后果**：清洗稿出现无中生有的「原话」，核证链彻底断裂——比错字严重一个量级（诚实标注原则的红线）。

**修复**：分段读时**头尾衔接段必须回查原文**（重读上一段末尾几行）；拿不准的区间宁可不写、标注「[衔接段未读，待补]」。

## P28 — 子代理输出超限终止与代理回报失真（2026-08-28~30 / 批量清洗 159 场 + 客户戊场）

**陷阱描述**：flash 子代理一次输出超 32K 被静默终止（无输出纪律批次 5/6 失败）；或子代理回报的金句时间戳与 01 实际不符（客户戊场 [00:51:33] 被错报为 [00:52:22] 两处）。

## P29 — CSS 同特异性后者覆盖：作用域扩大引入回归（2026-09-04 / 打样实测）

**陷阱描述**：修「作用域死区」时把 `.raw-body` 纳入行式样式（`:is(.transcript,.raw-body) .ts`，灰字无背景）。人物卡详情区容器恰好也是 `.raw-body`，其金句卡 `.quote .ts`（蓝底白字）与新规则**同特异性（0,2,0）且新规则写在后面**——白字被灰字覆盖，蓝底保留，呈现「蓝底灰字看不清」（用户肉眼发现）。

**后果**：修复一个缺陷的同时引入另一个渲染缺陷，且颜色值本身都「正确」，机械自检查不出（自检查色值存在性，查不出层叠顺序）。

**修复**：行式时间戳样式收窄到 `.line .ts`（行式徽章与金句卡徽章各管各的容器）。CSS 里已留注释说明为何必须带 `.line` 前缀。

**普适教训**：**改 CSS 作用域时，列出所有会命中的既有容器**，逐一核对是否有同特异性规则会被覆盖；改完必须人眼看一遍受影响区块（打样页肉眼走查是机械自检的必要补充）。
