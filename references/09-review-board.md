# 主管评审协议（review board）

多维度代理评审的机制化协议。定位：**L4 探针层**——评审是「不确定性的探针」，用来发现**新**问题；一旦某类问题有了机器检查（L3 闸门：verify_quotes / audit_content / pipeline_check），对应评审维度即可退役，不常设。

## 触发策略

| 场次类型 | 评审档位 |
|---|---|
| 合并包 / 重装档（大场） | **精简三主管**（数据事实 + 商业行动 + 知识工程）——历史发现密度最高的三维 |
| 用户点名「审一遍」 | 完整六主管 |
| 普通场 | 不跑（机器闸门全绿即可发布） |

## 六维度定义（2026-10-14 首轮多维度代理评审实战验证）

| 主管 | 视角 | 核心动作 | 带外部检索 |
|---|---|---|---|
| 信息架构 | 知识管理/IA | 模块体系/分层递进/分段粒度/单文件取舍 | 可选 |
| 编辑写作 | 中文商业写作 | 各模块逐个打分/口径一致性/AI 腔 | 否 |
| 数据事实 | 尽调核验 | python 扫 01 全部数字 vs 06；占比复算；出处逐条核 | 否 |
| 产品交互 | Web UX | HTML 体验路径走查/假交互/可访问性/移动端 | 可选 |
| 商业行动 | 咨询交付 | 扫承诺/死线语句 vs 09；商机线索；Owner 核对；风险盲区 | 否 |
| 知识工程 | 知识资产化 | 方法论逐卡合格率/漏立卡/反方分级/跨场资产 | 否 |

## 评审 prompt 要素（派发模板骨架）

1. 角色定位（专业视角一句话）+ 评审对象路径
2. 背景（场次/受众/管线产物结构）
3. 明确任务清单（每维度 3-6 项，含「系统性扫描而非抽查」的硬要求）
4. 输出契约：≤40 行；按「合理项/问题项（严重度排序+证据文件）/改进建议（可执行+成本标注）」
5. 只读纪律：不改任何文件
6. 数据/行动两维必须用 python 统计（grep 中文不可靠）

## 「评审→检查项」转化规则（核心纪律）

评审报告交回后 **7 天内**，每个发现必须三选一落地，不许只留在报告里：

1. **进脚本**（优先）：可自动检测的 → 沉淀为 audit_content / verify_quotes / pipeline_check 断言 + selftest 用例
2. **进契约**：写作纪律类 → 补进 references/02/03 对应模块节
3. **进坑库**：一次性踩坑类 → references/06 按 P 编号顺延

判定顺序：能进脚本的不进契约（机器比人可靠）；能进契约的不进坑库（前置纪律比事后记录强）。

## 已退役维度（有了机器闸门，精简评审不再必跑）

- ~~05 回合占比虚高~~ → audit_content 断言 A（err）
- ~~06 数据遗漏/出处错标~~ → audit_content 断言 B（warn 清单）+ 逐字出处纪律
- ~~09 死线漏收~~ → audit_content 断言 C（warn 清单）
- ~~00/09 Owner 冲突~~ → audit_content 断言 D
- ~~全模块引文时戳/逐字~~ → verify_quotes v3.3.3（00/00a/03/04/06/09/README 全覆盖）
- ~~附录 B 誊抄漂移~~ → verify_quotes 附录 B 检查（warn）
- ~~渲染假交互~~ → selftest 交互断言 + render_pack 修复（v3.3.2）

仍需代理的：编辑写作质量分级、信息架构分段粒度判断、洞察卡反方质量分级、商机线索的商业嗅觉——这些暂无机械判据。
