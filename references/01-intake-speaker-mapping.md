# 阶段 ① Intake + 说话人映射（最高风险阶段）

## Intake

### 输入形态与路由

| 输入 | 走法 |
|---|---|
| 飞书妙记 link | `lark-minutes` 拿逐字稿 → 走本阶段 |
| 飞书 doc 链接 | `lark-doc` 拿纯文本快照 → 走本阶段 |
| 本地 .md / .txt / .doc | 直接读 → 走本阶段 |
| 音频/视频文件 | `doubao-asr` 转写 → 走本阶段 |
| 粘贴文本 | 直接走本阶段 |

### Quick Assessment（不要问用户，自己判断）

读转写后判断并写入 01 头部：

- **说话人数量**：明确可识别几人？ASR 实际给了几个标签？是否少于实际在场人数？（**这是本阶段最重要的判断**）
- **时长**：< 30min / 30min–3h / > 3h
- **类型**：业务讨论 / 圆桌 / 访谈 / 咨询 / 闲聊
- **深度信号**：有决策？张力？矛盾？反复主题？

### 类型决定 09 是否出

- ✅ **咨询/诊断**（一方诊断、给建议、有行动）→ 出 `09_行动清单`
- ❌ **圆桌/直播/纯访谈/闲聊** → 不出 09（硬加会很别扭）；但本场凡产生待办仍应出

## 说话人映射（最高风险）

### Step 0：向用户要先验（可选，一句话提示）

Quick Assessment 后、开始指纹分析前，**问用户一句**（可选信息，不阻塞）：

> 「你方便给一份本场参会人名单吗？每人一句背景更好（如：张三，CTO，管基础设施）。
>  没有也没关系，我会从内容反推再找你确认——但有名单能显著降低映射出错率。」

**为什么值得问**：名单把映射从「开卷推理」变成「对号入座+验证」——

- **封闭世界**：候选集限定在名单内，不会臆造不在场的人，也不会把会议账号名当陌生人（账号名陷阱的先验解药）
- **指纹先验**：「张三管基础设施」→ 转写里讲服务器成本的大概率是他，指纹匹配从盲配变验配
- **防称呼误导**：知道「李四是顾问、王五才是合伙人」，称呼线索就骗不到你

**怎么用**：名单只作先验不作结论——仍要走 Step 1-4 全流程（指纹+时间线+二次确认）。用户给的名单也可能记错人（同 P11：用户提供的≠绝对真理），矛盾时以原文证据为准并回头和用户对齐。



### 典型反面案例（真实机制，人名已代号化）

某场四人对话，主持人（标签=账号实名，无误）、说话人2、说话人3、第四人：

| ASR 标签 | 两次误判 | 实际 |
|---|---|---|
| 主持人 | ✅ | 主持人 |
| 说话人2 | B（用户首次确认）✅ | B |
| 说话人3 | **D 顾问** ❌ | **C（主导商业规划的核心合伙人）** |
| 第四人 | C（"发言被并入"）❌ | D 顾问（发言少，未被 ASR 单独识别） |

**为什么连续错两次**：

1. 第一次：主持人在某回合当面称呼说话人3 为"D 顾问"——直接把称呼当身份
2. 第二次：基于第一个错，把真 C 当成"发言被并入的隐形人"
3. 真相：称呼只是称呼（可能是绰号/旧称/同音误听）；D 是另一个人，在场但话少

这个案例的教训不是「某个名字容易错」，而是**判定身份的依据必须是角色指纹与时间线，称呼只能当线索**。

### 方法论：角色指纹 + 时间线核对 + 用户二次确认

#### Step 1：列每个 ASR 标签的「角色指纹」

| 指纹维度 | 提取什么 |
|---|---|
| 主导什么内容 | 技术？商业规划？主持？咨询？ |
| 自述身份 | "我公司""我们公司""我跟某某合作""我做了 X" |
| 被他人称呼 | 谁叫你？叫你什么？（仅作线索，不作结论） |
| 第一次出现时间 | `[HH:MM:SS]` 上车 / 插话 / 加入 |
| 语用风格 | 短接话 vs 长论证 vs 提问推动 |

#### Step 2：交叉校验（必须做）

| 校验项 | 怎么查 |
|---|---|
| **主导 vs 标签** | 用户说"主导 X 的是 Y" → Y 对应的 ASR 标签 = X 的主导者 |
| **时间线一致性** | 如果 X 在 `[00:20:07]` 才到场，则之前的 X 标签回合可能不是 X（或 X 早就在场但 ASR 误标） |
| **称呼 ≠ 身份** | A 被 B 叫"某老师"≠ A 就是那位老师 |
| **自述内容 vs 指纹** | 说话人自述的合伙关系/职务应与其内容指纹锁定 |

#### Step 3：用户二次确认（绝不能省）

**哪怕指纹分析感觉很确定，也要让用户确认。** 要点：

1. 第一次只问**最不确定的那一个**（通常是被 ASR 标"说话人N"的），不要一次问完所有映射
2. 用户的首次回答可能基于不完整信息（只看了开头、记不清），**不能当绝对真理锁死**——保留追问余地
3. 一旦发现新矛盾（如"主导 X 的应该是 Y"对不上当前映射），立即回原文复核，而不是猜测

#### Step 4：识别身份存疑的发言（不要硬拆）

有些回合确实无法判断是谁说的（ASR 合并 + 无音频）：

- **不要硬拆**——保留原归属，在附录"说话人说明"里标注
- 不要为了"还原得漂亮"而臆造身份
- 把无法确定的回合明确划入"未识别"

### 改名映射后的「称呼与标签不一致」说明

修正映射后，原话里的称呼词**必须保留**（金句原则：原话一字不改）。但头部必须显式说明，例如：

```markdown
- **说话人3 → C** = …[00:20:07] 到场；本场商业规划主导者…
- **D** = 在场参与，发言不多，ASR 未单独识别。注意：原文中主持人多次以"D 老师"相称，
  该称呼实际指向 C（说话人3）；个别处（C 自述"咨询由 D 老师提供"）指真正的 D。
  原话中"D 老师"称呼词一律保留不改，由本说明区分。
```

读者看 `**【C】** [01:28:08]` 但话里说"D 老师很厉害"——结合头部说明，立刻理解称呼指向。

## 时间线核对（必查）

| 时间线冲突类型 | 例子 | 处理 |
|---|---|---|
| X 在 [00:20:07] 才到场，但 [00:15:32] 有人叫 X 发言 | 误识别 → 撤销 | 恢复原 ASR 归属，标注"口误/存疑" |
| X 自述"我们公司一亿"但 Y 才是那个公司的人 | 矛盾 → 查上下文 | 看完整段判断 |
| 同一句话两人轮换太快，ASR 标错 | 错位 | 逐字比对原文转写 |

**任何说话人改动，都要重新跑时间线核对。**

## 标签结构异常（五类）

ASR 标签的问题不止「映射到谁」，还有**结构性异常**——标签与真人不呈一一对应。遇见先对号入座再动手：

### 类型一：多人压一标签，按时段切分

一个 ASR 标签在不同时段其实是不同的人（多人参会压成一两个标签；开场轮流自介段实为 N 人）。

**判据**：同一标签的发言内容/口吻跨时段断裂 + 外部交叉源（另一份带编号发言人 的录制稿）或自介段锚点句。
**处理**：按时段拆分、各标【姓名】，头部写明切分依据；多人自介段可合并为「与会者轮流自介」。

### 类型二：双身份标签

同一标签中段与压轴是两个人。

**判据**：内容指纹（业务自述）在段内突变 + 交叉源锚点。
**处理**：按内容指纹归位、各自标注，时间线写进头部。

### 类型三：视频原声误归

外放视频（短视频/演示片）的声音被 ASR 全归到在场者名下。

**判据**：①在场者插话提示（如「两倍速」）；②内容第一人称自述与在场者立场相反；③真声间隙有该人插话。
**处理**：改标【视频原声】，**不计入该人发言量与回合比**（否则污染 05 人物卡占比）。

### 类型四：会后 AI 语音混录

录音结束后的智能体测试语音被当作正常说话人。

**判据**：内容与会议主题脱节 + 集中在末尾 + 表达风格机械。
**处理**：移入附录，正文标注剔除依据。

### 类型五：旁听者 / 英文场无标签

录音者本人旁听未发言时，ASR 不给独立标签；英文场（ASR 英文转写破碎）同样可能说话人缺失。

**处理**：旁听者身份写进头部说明（「某人旁听，被提及未发言」）；英文场清洗走 `references/02` 的边缘类型规范。

## 第三种陷阱：转写标签 ≠ 本人（账号名陷阱）

**陷阱描述**：转写标签看起来是完整姓名，但其实是某位参会者的**会议账号名**——部分转写平台按参会账号名标注，不按真实身份。

**典型信号**：

1. 头部映射块写「docx『某姓名』N 回合」但本人从未自称过此名
2. 标签形式是完整姓名，但与会者当面都不叫此名（只叫别的称呼）
3. **跨场检索**：在项目内 grep 此名——无任何其他匹配 → 高概率是账号名；反之若在其他场次也出现 → 多半是真人本名，按普通映射处理

**处理**：

- 头部映射块显式标注：「转写标签『X』= 该参会者的会议账号名」（注明用户已确认）
- 正文回合全部改标真实姓名；原话中出现的账号名语境字样保留原样（金句原则）

## 开工前必查

任何场次开工前：

1. **查项目内既有记录**——项目的人物映射笔记/词表是否已登记该人的 ASR 变体、账号名陷阱（多场次项目尤其重要，见 `references/07`）
2. **查主题总 README**——链表是否已含本场次目录（防重复清洗）
3. 入场后跑 `scripts/pipeline_check.sh <场次目录>` 做结构与同步基线
